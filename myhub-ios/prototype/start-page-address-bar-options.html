内置浏览器 · 空白页（起始页）地址栏位置优化

现状：空白标签的输入框是 StartPage.searchBar，贴在安全区顶部 + 16pt（单手拇指基本够不到）， 且它外面套了 .contentShape(Rectangle()) + .onTapGesture { Keyboard.dismiss() }， 点击很容易被这层手势吃掉（点了没反应、要连点几次）——两个问题叠加成「在最上面不好点击」。
下列 4 个方案都顺带修掉「手势吞点击」（改成 simultaneousGesture / 只挂背景层）。 蓝色虚线框 = 建议的点击热区，绿色虚线框 = 单手拇指自然可达区。

现状Before

输入框距屏幕顶边约 75pt（状态栏 47 + 16 + 卡片），46pt 高。
底部操作栏在起始页把中区地址栏换成了 Spacer，只剩三个导航键和标签/菜单， 中间一段空着——离拇指最近的位置反而不可点。
问题：①位置过高；②点击被外层手势吞掉；③底部空占一条 60pt 的胶囊却不承担输入。

方案 A · 下移加大最小改动

输入框从安全区顶部 16pt 下移到 72pt（落在拇指向下扫的第一落点），高度 46 → 52pt， 圆角同步放大；顶部空出来的区域放一行极简的「无痕 / 标签数」状态，避免空荡。
优点：只改 StartPage 的 padding 与输入框高度，零结构风险；顺带修点击手势。
缺点：仍在屏幕上半区，大手 / 单手握持时仍需要换手；对「不好点」只解决一半。

方案 B · 输入框吸底推荐

起始页不再画独立搜索框，改为底部操作栏在空白页也显示可点的地址栏（BrowserToolbar 去掉 Spacer 分支）。点它即进入编辑态、键盘弹起，内容区只剩快捷入口。
优点：输入框直接落在拇指区（Chrome iOS 同款）；消除了「底部一条 60pt 胶囊中间空着」的浪费； 起始页与网页页的操作栏形态完全一致，切换时不再有形变跳变。
缺点：视觉上少了一个「大搜索框」的引导，首次使用需要认出胶囊里的地址栏（可用占位文案「搜索或输入网址」弥补）。

方案 C · 居中大搜索搜索优先

输入框垂直居中偏上（约屏高 32% 处），字号 17、高度 56，视觉上像 Spotlight； 上方留白承载站点统计，快捷入口整体下移到输入框之下。
优点：可点性明显改善（落在手自然抬起的位置）；「空白页」的空白被利用，搜索意图最强。
缺点：快捷入口被挤到下半屏，需要滚动才能看全；与常见浏览器起始页布局差异较大，学习成本高。

方案 D · 双入口兼容并包

顶部搜索框保留（仅下移到 56pt、加高到 50pt），同时让底部操作栏在起始页显示地址栏： 爱用哪一个都行，两条入口共用同一个编辑态与同一个输入框组件。
优点：不需要用户改习惯；顶部留给「看着舒服」，底部负责「单手够得到」；两者都修好点击热区。
缺点：同屏两个输入入口，信息重复；底部胶囊与顶部搜索框并存的视觉密度偏高。

方案可点性改动范围视觉风险备注
现状差（距顶 75pt + 手势吞点击）——底部胶囊中区空占
A 下移加大中仅 StartPage 布局低改动最小，可先上线
B 输入框吸底好StartPage + BrowserToolbar（去掉起始页 Spacer 分支）中（少了大搜索框引导）推荐，与 Chrome iOS 一致
C 居中大搜索好仅 StartPage 布局高（快捷入口被挤）视觉变化最大
D 双入口好StartPage + BrowserToolbar中（重复入口）不改用户习惯

关于「点击被吞」的实现修复（4 个方案都需要）： 现在 StartPage 在 VStack 上挂了 .contentShape(Rectangle()) + .onTapGesture { Keyboard.dismiss() }， 这层手势与 TextField 的点击在同一链路上竞争，容易出现「第一下只收起键盘、没进入输入态」。 改法：收键盘的手势只挂在背景层（Color.clear.contentShape(Rectangle()).onTapGesture 垫在内容之下）， 或把 onTapGesture 换成 simultaneousGesture，不再吃掉输入框与快捷入口的点击。
方案 B 的额外好处：起始页与网页页共用同一条操作栏，切标签时的「展开 ⇄ 小胶囊」形变也不再出现（与本次另一处修复呼应）。 确认方案后我再改 StartPage.swift / BrowserToolbar.swift。
